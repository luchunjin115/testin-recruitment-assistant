## 2. 总体目标

用 React、FastAPI、PostgreSQL 和 DeepSeek 建设可真实操作的招聘平台，先完成招聘业务闭环，再接入综合 Agent、RAG、权限和交付能力。

```text
基础平台
  -> 简历上传与结构化
  -> 岗位与 Application
  -> AI 初筛与 HR 决策
  -> 公开投递与异步处理
  -> 面试、Offer、录取
  -> 综合 Agent
  -> RAG
  -> 权限、部署和交付
```

## 3. 阶段门禁

每个阶段进入业务开发前必须完成：

1. 业务目标、用户场景、主流程和异常流程讨论。
2. 包含范围、不包含范围和前后阶段依赖确认。
3. 数据字段、状态、权限、API 和失败语义确认。
4. 自动化测试、真实集成和人工验收场景设计。
5. 独立阶段设计文档。
6. 用户明确确认。

任何会改变核心流程、数据模型、阶段边界或验收标准的需求，必须先回到文档门禁。

## 5. 当前跨阶段整改顺序

阶段 7 已完成旧 Rubric 清理、3.0 JobEvaluationPlan、AI 报告、异步运行、React 报告和固定投递时间事实。阶段 6 五段式 JD 已完成；3.0 的 7R-A—7R-E 程序与页面门禁已经完成，但 7R-F 首轮定向真实质量只有 3/6 满足合同，正式 20 份被门禁阻止。后续讨论确认不能继续让一次模型调用同时负责事实提取、完整性和展示归组，因此当前改为 RequirementFact + EvaluationCriterion 双层 4.0。

当前顺序调整为：

1. 6R-A 已完成：测试固定五字段、开放校验、旧字段退出和阶段 7 安全暂停合同。
2. 6R-B 已完成：后端与 PostgreSQL Job 合同原子切换，旧 JobEvaluationPlan 读取新 Job 的入口被阻止。
3. 6R-C 已完成：React 岗位表单、列表和现有读取方切换到五个大型文本框。
4. 6R-D 已完成：后端/前端全量、真实 PostgreSQL、真实 API、Microsoft Playwright 三档浏览器验收和阶段 7 交接通过。
5. 3.0 的 7R-A—7R-E 已完成，7R-F 定向真实质量失败；旧结果保持为历史证据，不继续执行旧 7R-G/H。
6. 4.0 的事实层、评价维度层、三次调用、一次局部修复、HR 确认、31+ warning、历史兼容和质量门槛已逐项确认；权威设计已写入 2026-08-24 补充。
7. 当前唯一下一步是用户复核并明确确认 7R4-A—7R4-J 实施顺序；确认后只执行 7R4-A 合同测试与离线容量基线，后续每批继续单独确认。
8. 7R4-H 先验证原 6 份定向样本，6/6 通过后才验证正式 20 份计划；7R4-I 再验证 20 组 JD/Resume 的合法报告率、方向一致性和三次稳定性；7R4-J 完成真实 PostgreSQL/API 和全部浏览器欠账。真实 DeepSeek 只允许在 7R4-H/I 且单独确认模型与成本后调用。

4.0 实施顺序最终确认和对应批次完成前，不得以 3.0、未确认计划、部分计划或 Fake/Mock 结果冒充 4.0 可用；仍在招聘的旧职位必须重新生成并确认 4.0 后才能继续新的 AI 初筛。

## 7. 每个小步骤的完成标准

每个开发小步骤至少说明：

1. 修改了哪些文件，各自承担什么职责。
2. 位于“前端 -> API -> Schema -> Service -> Model -> PostgreSQL”哪一层。
3. 自动化、构建、真实数据库或浏览器中的验证方法与结果。
4. 验证能够证明什么、不能证明什么。
5. 是否改变当前阶段设计；若改变，是否先更新文档并获得确认。
6. 简历中如何如实表达，以及面试官可能追问什么。

## 8. 全产品完成标志

- HR 能创建岗位并接收投递。
- 简历能够可靠保存、提取、结构化和进入对应岗位初筛。
- AI 报告可解释、可定位证据且不替代 HR 决策。
- Application 能推进到面试、Offer 和最终结果，并保留审计历史。
- 综合 Agent 只能通过受控 Tools 使用真实业务能力。
- 公司知识问答和简历语义搜索返回可追溯来源。
- AI、队列或外部服务失败不丢失业务事实和旧成功结果。
- 未授权用户不能访问内部数据或执行高风险操作。
