## 2. 总体目标

用 React、FastAPI、PostgreSQL 和 DeepSeek 建设可真实操作的招聘平台，先完成招聘业务闭环，再接入综合 Agent、RAG、权限和交付能力。

```text
基础平台
  -> 简历上传与结构化
  -> 岗位与 Application
  -> AI 初筛与 HR 决策
  -> 公开投递与异步处理
  -> 面试、Offer、录取
  -> 综合 Agent
  -> RAG
  -> 权限、部署和交付
```

## 3. 阶段门禁

每个阶段进入业务开发前必须完成：

1. 业务目标、用户场景、主流程和异常流程讨论。
2. 包含范围、不包含范围和前后阶段依赖确认。
3. 数据字段、状态、权限、API 和失败语义确认。
4. 自动化测试、真实集成和人工验收场景设计。
5. 独立阶段设计文档。
6. 用户明确确认。

任何会改变核心流程、数据模型、阶段边界或验收标准的需求，必须先回到文档门禁。

## 5. 当前跨阶段整改顺序

阶段 6 已完成。阶段 7 的 1.0—4.0 只保留历史证据；5.0 已完成数据、API、Service、异步运行和 React 主链。I4 唯一真实 raw 为计划 `10/10`、报告合法 `19/20`、稳定性合法 `13/15`，但用户在实际使用后明确判定 AI 初筛仍有问题，阶段 7 当前不能验收通过。人工界面验收已完成，不改变 AI 质量整改重新打开的事实。

当前唯一跨阶段顺序为：

1. 收集 AI 初筛具体问题场景，记录实际输出、期望结果、业务影响和可复现性；只读归因，不先修改代码。
2. 编写并确认新的阶段 7 整改设计和实施批次，明确责任层、红灯、回归、人工验收、真实模型预算和停止点。
3. 用户逐批确认后实施整改；需要真实模型复验时重新查询官方价格并获得独立 USD 授权，不覆盖 I4。
4. 新质量验收达到用户最新产品标准后，重新执行并封存 CLOSE-07；随后停止等待用户另行确认 CLOSE-08。
5. CLOSE-08 逐项核对阶段完成标准；阶段 8—12 不自动开始，阶段 8 仍须重新完成需求确认门禁。

不得以 3.0、4.0、部分 5.0、Fake/Mock、Service 接受或零调用旧响应回放冒充阶段 7 完成；完整业务边界见 5.0 主设计，当前逐批依赖和停止点只见剩余工作计划。

## 6. 跨阶段依赖

- 阶段 7 依赖阶段 4—6 的 Resume、结构化草稿和五段式 Job；当前先完成新一轮 AI 初筛问题归因、整改和质量验收，再重新封存 CLOSE-07，之后才能进入 CLOSE-08 完成评审。
- 阶段 8 复用阶段 7 的 Application、评价计划和报告引擎，再增加公开投递与持久化队列。
- 阶段 9 从 HR 已通过的 Application 开始面试、Offer 和录取流程。
- 阶段 10 通过受控 Tool 复用既有 Service，不复制业务规则。
- 阶段 11 复用 `raw_text/parsed_snapshot` 和权限边界，不改变正式初筛口径。
- 阶段 12 对完整主链补充认证、授权、审计、部署和端到端验证。

## 7. 每个小步骤的完成标准

每个开发小步骤至少说明：

1. 修改了哪些文件，各自承担什么职责。
2. 位于“前端 -> API -> Schema -> Service -> Model -> PostgreSQL”哪一层。
3. 自动化、构建、真实数据库或浏览器中的验证方法与结果。
4. 验证能够证明什么、不能证明什么。
5. 是否改变当前阶段设计；若改变，是否先更新文档并获得确认。
6. 简历中如何如实表达，以及面试官可能追问什么。

## 8. 全产品完成标志

- HR 能创建岗位并接收投递。
- 简历能够可靠保存、提取、结构化和进入对应岗位初筛。
- AI 报告可解释、可定位证据且不替代 HR 决策。
- Application 能推进到面试、Offer 和最终结果，并保留审计历史。
- 综合 Agent 只能通过受控 Tools 使用真实业务能力。
- 公司知识问答和简历语义搜索返回可追溯来源。
- AI、队列或外部服务失败不丢失业务事实和旧成功结果。
- 未授权用户不能访问内部数据或执行高风险操作。
