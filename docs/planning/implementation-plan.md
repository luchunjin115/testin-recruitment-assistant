## 2. 总体目标

用 React、FastAPI、PostgreSQL 和 DeepSeek 建设可真实操作的招聘平台，先完成招聘业务闭环，再接入综合 Agent、RAG、权限和交付能力。

```text
基础平台
  -> 简历上传与结构化
  -> 岗位与 Application
  -> AI 初筛与 HR 决策
  -> 公开投递与异步处理
  -> 面试、Offer、录取
  -> 综合 Agent
  -> RAG
  -> 权限、部署和交付
```

## 3. 阶段门禁

每个阶段进入业务开发前必须完成：

1. 业务目标、用户场景、主流程和异常流程讨论。
2. 包含范围、不包含范围和前后阶段依赖确认。
3. 数据字段、状态、权限、API 和失败语义确认。
4. 自动化测试、真实集成和人工验收场景设计。
5. 独立阶段设计文档。
6. 用户明确确认。

任何会改变核心流程、数据模型、阶段边界或验收标准的需求，必须先回到文档门禁。

## 5. 当前跨阶段整改顺序

阶段 7 已完成旧 Rubric 清理、JobEvaluationPlan、AI 报告、异步运行、React 报告和小步骤 8；小步骤 9-I 的正式 JD 门禁因 JD18 失败而未通过。随后业务讨论确认，根因不能只在 Prompt 中修补：阶段 6 的 `description + JobRequirementsV1` 本身不符合 HR 实际填写 JD 的方式。

当前顺序调整为：

1. 完成阶段 6 五段式 JD 整改文档门禁：当前正在等待用户最终复核 6R-A—6R-D 实施批次。
2. 6R-A：只用测试固定五字段、开放校验、旧字段退出和阶段 7 安全暂停合同。
3. 6R-B：原子切换后端与 PostgreSQL Job 合同，并阻止旧 JobEvaluationPlan 继续读取已退出字段。
4. 6R-C：将 React 岗位表单、列表和现有读取方切换到五个大型文本框。
5. 6R-D：完成后端/前端全量、真实 PostgreSQL、浏览器验收和阶段 7 交接。
6. 阶段 6 整改完成后，重新讨论并更新阶段 7 五段式 JD 评价计划设计；获得用户确认前不得实现新 Prompt、Schema、Service 或真实 DeepSeek 调用。
7. 新阶段 7 上游合同通过后，再重新安排 JD 质量、合法报告率、方向一致性、重复稳定性和浏览器完整复验。

阶段 6 整改期间，岗位管理继续作为目标能力建设；阶段 7 旧 JD 生成入口必须受控暂停，不得以旧字段、旧计划或 Fake/Mock 结果冒充新合同可用。

## 6. 跨阶段依赖

- 阶段 7 依赖阶段 4—6 的 Resume、结构化草稿和 Job；当前必须先完成阶段 6 五段式 JD 整改，才能恢复评价计划生成。
- 阶段 8 复用阶段 7 的 Application、评价计划和报告引擎，再增加公开投递与持久化队列。
- 阶段 9 从 HR 已通过的 Application 开始面试、Offer 和录取流程。
- 阶段 10 通过受控 Tool 复用既有 Service，不复制业务规则。
- 阶段 11 复用 `raw_text/parsed_snapshot` 和权限边界，不改变正式初筛口径。
- 阶段 12 对完整主链补充认证、授权、审计、部署和端到端验证。

## 7. 每个小步骤的完成标准

每个开发小步骤至少说明：

1. 修改了哪些文件，各自承担什么职责。
2. 位于“前端 -> API -> Schema -> Service -> Model -> PostgreSQL”哪一层。
3. 自动化、构建、真实数据库或浏览器中的验证方法与结果。
4. 验证能够证明什么、不能证明什么。
5. 是否改变当前阶段设计；若改变，是否先更新文档并获得确认。
6. 简历中如何如实表达，以及面试官可能追问什么。

## 8. 全产品完成标志

- HR 能创建岗位并接收投递。
- 简历能够可靠保存、提取、结构化和进入对应岗位初筛。
- AI 报告可解释、可定位证据且不替代 HR 决策。
- Application 能推进到面试、Offer 和最终结果，并保留审计历史。
- 综合 Agent 只能通过受控 Tools 使用真实业务能力。
- 公司知识问答和简历语义搜索返回可追溯来源。
- AI、队列或外部服务失败不丢失业务事实和旧成功结果。
- 未授权用户不能访问内部数据或执行高风险操作。
