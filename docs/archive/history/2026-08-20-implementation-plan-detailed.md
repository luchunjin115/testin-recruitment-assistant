## 总体目标

用新版架构直接替代旧版招聘助手，形成面向公司内部 HR 团队的 AI 招聘工作台。旧 React + FastAPI + SQLite + Mock LLM 演示系统及演示数据不再维护或迁移。最终产品要打通“岗位创建 -> 候选人投递 -> 自动初筛 -> HR 决策 -> 面试 -> Offer -> 录取”的招聘链路，并在首页提供能够调用真实业务工具、生成 JD 草稿、查询候选人和通过 RAG 检索公司内部文件的综合 Agent。

技术目标是从旧版 `React + FastAPI + SQLite + Mock LLM` 升级为：

- 前端：React 18 + TypeScript + Ant Design 5 + Vite + zustand
- 后端：FastAPI + SQLAlchemy 2.0 + Pydantic v2 + Alembic
- 数据：PostgreSQL 16 + Redis + Chroma
- AI：DeepSeek API；LangGraph 按真实工作流复杂度使用，不强制包装普通单次模型调用
- 部署：Docker Compose

核心原则：先做可靠的招聘业务闭环，再把 AI 放进关键节点。不要先追求“会聊天”，而是先保证 HR 可以真实完成“上传简历 -> 解析 -> 匹配 -> 报告”的主流程。

## 阶段 0：项目对齐与基线整理

### 要做什么

1. 确认权威设计文档路径。
2. 检查旧版项目结构和关键文件。
3. 梳理可迁移资产、需重写模块、保留历史模块。
4. 建立或更新项目状态文档。
5. 明确后续阶段的执行顺序和验收口径。

### 为什么这样做

当前项目不是空项目，而是已有一版演示系统。旧系统里有很多可复用资产，比如 Prompt、文件解析、候选人投递页和规则评分逻辑。但旧系统的架构和最终目标不一致，如果直接在旧代码上堆功能，很容易变成“能跑但不好维护”的系统。

阶段 0 的价值是先划清边界：哪些东西要搬家，哪些东西要重写，哪些东西只作为参考。这样后面每一步都有依据。

### 可能遇到的问题

- 旧版 `PROJECT_STATE.md` 显示“已完成”，但这是旧演示版本，不代表新架构完成。
- 旧版后端目录是 `routers/`、`services/` 结构，新设计要求 `api/`、`core/`、`agents/`、`rag/` 等分层。
- 旧版数据库默认偏 SQLite，本次目标是 PostgreSQL + Alembic。
- 旧版 AI 服务职责混杂，需要按业务边界重写；普通单次模型能力放在 Service，确有条件路由、循环或多工具协作的复杂流程才使用 LangGraph。

### 验收标准

- `CLAUDE.md` 指向的设计文档存在。
- 项目状态文档明确标记“架构重建阶段”。
- 迁移清单清楚列出复用、重写和参考文件。
- 后续阶段能按计划继续，不需要重新判断方向。

## 阶段 4：简历上传与文件解析

### 要做什么

- 通过 `POST /api/v2/resumes/upload` 安全接收 PDF、DOCX、TXT，校验真实文件类型、大小和私有存储路径。
- 通过 `POST /api/v2/resumes/{resume_id}/extract-text` 把文件转换为 `Resume.raw_text`，记录 `uploaded/parsing/parsed/failed` 文件解析状态和稳定错误。
- 支持 `candidate_id = NULL` 的待绑定 Resume，使 HR 可以先上传和提取原文，再确认候选人。
- 通过 `POST /api/v2/candidates/from-resume` 在一个数据库事务中创建 Candidate、三类经历并绑定 Resume；阶段 4 不识别结构化字段。
- 提供原始简历的安全查看/下载、主动放弃未绑定 Resume 和 24 小时过期自动清理。
- 本阶段历史实现曾让旧 `/api/resume/*` 与新版 `/api/v2/resumes/*` 隔离并存；2026-08-18 退役决策后，旧接口只等待统一入口切换和删除，不再作为兼容目标。
- 普通 DOCX 使用 `python-docx` 保留正文/表格顺序；含 Word/VML 文本框或普通正文为空的模板简历使用 Mammoth 提取可见文字，并保留原有文件与 ZIP 安全边界。

### 为什么这样做

简历上传是整条链路的入口。阶段 4 只负责“文件 → 可信原文”，并保证文件、数据库记录和候选人确认绑定之间的安全边界；阶段 5 才负责“原文 → 结构化草稿”。

### 可能遇到的问题

- PDF 有扫描件、表格、乱码等情况。
- DOCX 可能有表格、合并单元格、文本框或复杂压缩包结构；纯图片型 DOCX 仍需要后续 OCR。
- 上传失败、解析失败需要明确状态，不应该悄悄吞掉错误。
- 文件系统与 PostgreSQL 无法组成真正的跨系统原子事务，需要补偿清理和孤立文件边界。
- 未绑定 Resume 需要主动放弃和过期清理，同时不能误删已绑定或正在使用的文件。

### 验收标准

- PDF、DOCX、TXT 至少各有一个样例能成功解析。
- 原始文件、元数据、`raw_text` 和文件解析状态真实保存，读取和下载不暴露私有路径。
- 待绑定 Resume 能在 HR 确认后与 Candidate 及经历记录单事务保存，失败不会留下半绑定数据。
- 主动放弃和 24 小时清理不会删除已绑定 Resume，数据库失败时能够补偿恢复文件。
- 前端能展示上传、提取、失败、查看、下载、放弃和确认创建的真实状态。

## 阶段 5：大模型简历结构化提取与表单辅助填写

> 完成状态：✅ 2026-08-14 已完成。真实 PDF、DOCX 简历已通过页面操作验证，DeepSeek、FastAPI、PostgreSQL、Vite 主链路和人工确认流程可用；DOCX 文本框兼容、识别耗时展示和右侧滚动问题已完成修正。当前接受 DeepSeek 单份简历约 10～12 秒的响应速度，速度优化、轻量模型替换、OCR 与 15～20 份脱敏样本统计评估转为后续质量增强项，不阻塞阶段 6。

### 要做什么

阶段 5 复用阶段 4 已保存的 `Resume.raw_text`，不重复处理文件。第一版不使用 Agent 或 LangGraph，建立普通 `ResumeStructureService`：

1. 定义版本化、严格的 `ResumeParseDraft`，包含基本资料、教育、工作、项目、技能、证书、自我评价、警告和缺失字段。
2. 通过模型 Adapter 正常只调用一次 DeepSeek，使用 JSON Output，把完整原文转换成统一草稿。
3. 依次执行 JSON 解析、Pydantic 严格 Schema 校验和日期、重复项、长度、空记录等业务校验；未知字段禁止静默进入系统。
4. 成功草稿保存到 `Resume.parsed_snapshot`；新增独立的结构化识别状态、错误和版本字段，不复用阶段 4 的文件 `parse_status`。
5. 新增 `POST /api/v2/resumes/{resume_id}/structure`。已有成功草稿时默认直接返回，只有 HR 明确点击“重新识别”才再次调用模型；同一 Resume 并发识别返回 `409`。
6. 前端在阶段 4 原文提取成功后触发识别，将 AI 结果只补充到空字段。HR 已填写的普通字段不得覆盖；已有经历列表时不得静默拼接，由 HR 选择是否导入。页面以“内容读取 → 信息识别 → 人工核对”的业务语言展示流程，提取文本默认折叠，仅作为核对依据。
7. AI 只生成草稿，不直接创建或改写 Candidate 及三类经历；HR 检查、修改并确认后，才复用现有单事务接口创建 Candidate 并绑定 Resume。
8. 结构化成功响应附带当前请求的总耗时、数据准备、模型调用、结果校验和结果保存耗时；命中旧草稿时明确标记缓存读取，计时只用于本次诊断，不写入业务数据。

完整设计与字段、状态、API、异常和验收规则见 `docs/specs/2026-08-12-stage5-resume-structure-design.md`。

### 为什么这样做

当前输入和输出都是固定的：`Resume.raw_text -> ResumeParseDraft`。第一版用一次模型调用即可验证真实简历上的完整性、延迟和费用；此时引入 Agent 或多节点 LangGraph 会增加调用次数和调试成本，但没有相应的自主决策价值。通过稳定的 Service/API 抽象保留演进空间，只有真实样本证明存在稳定的局部遗漏或局部重试需求后，才评估内部升级为多节点工作流。

### 可能遇到的问题

- LLM 输出不是合法 JSON。
- JSON 合法但字段类型、日期关系或业务内容不合法。
- 模型可能返回空内容、输出被截断、超时、限流或服务错误。
- 同一信息在简历里重复出现。
- 某些字段无法确定，要填 `null`，不能编造。
- AI 结果可能与 HR 已填写字段或经历列表冲突。
- 大模型服务失败不能破坏阶段 4 已保存的原文件和原文。

### 验收标准

- 每次正常识别只调用一次 DeepSeek，不使用 Agent 或 LangGraph。
- 模型错误、空响应和非法输出无法写入草稿或自动填表；失败后原文件、原文和人工输入保持不变。
- 合法草稿写入 `Resume.parsed_snapshot`，页面刷新后可以重新取得；结构化状态与阶段 4 文件解析状态语义分离。
- 前端能辅助填写基本资料、教育、工作、项目和技能，但不覆盖 HR 已填写字段，也不静默合并已有经历列表。
- 应聘岗位、来源和招聘状态不由模型猜测；性别和年龄不得用于后续评分。
- 学校名称在本阶段只按原文提取，不推断 985/211；后续如用于初筛，必须通过可追溯的标准院校数据判断。
- AI 不直接创建 Candidate；只有 HR 最终确认才写入正式候选人和经历表。
- Fake Adapter 的自动化测试、真实 DeepSeek + FastAPI + PostgreSQL 验证、前端生产构建和人工操作验收均通过。
- 页面能区分真实识别与缓存读取，并展示足以定位主要性能瓶颈的分阶段耗时。

## 阶段 6：结构化岗位管理

> 完成状态：✅ 2026-08-17 用户已确认阶段 6 完成。岗位管理主链路、下游开放岗位读取边界、后端全量 418 项、前端 9 项、生产构建、真实 PostgreSQL 与真实 API 集成验收均已通过；此前 Codex 受控浏览器没有可用实例的限制保留在 `PROJECT_STATE.md` 和阶段 6 验收记录中。

### 当前方向

- 固定严格、版本化的岗位要求 Schema。
- HR 直接填写岗位基础信息、必备要求和加分要求，不使用 AI 解析 JD。
- 支持 `draft/open/closed` 状态及开放、关闭和安全删除规则。
- 接通 `/api/v2/jobs` 真实写入和 `/stage3/jobs` 表单。
- AI 初筛中心和公开投递只读取开放岗位。

### 阶段开始前必须确认

`JobRequirements v1` 字段、开放完整性、关闭/重新开放/删除规则、旧 JSONB 数据兼容、API 行为和人工验收场景。

### 当前完成标准

HR 能创建、编辑、开放和关闭一个完整岗位；刷新后数据真实保存在 PostgreSQL；草稿和关闭岗位不能进入新投递或新初筛。最终标准以阶段 6 专项设计为准。

## 阶段 7：Application 与 AI 初筛底座

> 进行状态：🚧 2026-08-20 用户已逐项确认 JD 驱动的 AI 综合评价方案。旧 Rubric、五维权重、内部占比、确定性评分、`unknown`、证据覆盖率和多报告历史已废弃；Application、Resume 隔离、HR 录入和 HR 决策公共能力继续保留。当前只完成文档门禁，业务代码尚未按新方案修改。

### 当前方向

- 以 Job/JD 为唯一岗位事实来源；DeepSeek 拆解自由文本，程序补齐结构化 JobRequirements，合并为同一 JD 版本下稳定、只读的基础评价事项。
- 基础事项使用 `required/preferred/general` 和逐项 `0—10`，不使用 `unknown`；1—10 分必须有可定位简历证据，0 分表示当前简历未体现。
- 每份简历允许 0—5 个有证据、7—10 分、只产生正向影响的候选人额外亮点；不能在 JD 之外创造扣分标准。
- DeepSeek 直接给出 `0—100` AI 岗位匹配建议分；程序只生成五档展示标签，不加权重算，也不自动淘汰。
- AI 返回严格 JSON，后端校验结构、事项完整性、证据、敏感信息和明显矛盾；React 渲染完整 AI 初筛报告。
- 每个 Application 只保留最近一次成功报告和最小运行日志；重新评估成功后替换，失败时保留旧成功报告。
- 第一次条件满足后异步自动初筛；支持单人和最多 20 人小批量重新评估，岗位关闭时暂停未运行任务。
- Candidate、Application、Resume 隔离和 HR 决策边界继续保留；AI 不生成通过、淘汰或录用建议。
- 旧 Rubric 代码和业务数据先完成精确盘点与删除，再开发新评价计划和报告链路。

### 当前完成标准

旧 Rubric 体系和数据结构已删除且公共链路回归通过；HR 发布 JD 后能获得稳定的只读评价事项；可用 Resume 能生成一份结构化、可解释、证据可定位的完整报告；新报告成功替换、失败保留旧成功结果；AI 不改变 HR 决策。自动化、真实 PostgreSQL、真实 DeepSeek、20 份 JD、20 组脱敏 JD/Resume、重复稳定性和浏览器人工验收全部达到新专项设计标准后，阶段才算完成。

专项设计和小步骤顺序以 `docs/specs/2026-08-20-stage7-jd-driven-ai-screening-redesign.md` 为准。下一小步只做旧 Rubric 引用盘点和删除清单，不直接删除文件。

## 阶段 8：公开投递和自动初筛

### 当前方向

- 展示开放岗位并接收真实公开投递。
- 强制投递者填写姓名、手机号和邮箱并上传简历，随后自动创建或安全复用 Candidate，再创建 Application 和 Resume，不要求 HR 逐份确认资料录入。
- 通过 Redis 持久化任务队列和后台 Worker 异步执行原文提取、结构化和岗位匹配。
- 复用阶段 7 已验证的 Application 状态机、Rubric 与评分引擎，扩展为可恢复的大规模处理。
- 提供 HR 初筛处理池、任务进度和异常处理区。
- 保证幂等、失败隔离、可重试和数据不丢失。

### 当前完成标准

候选人提交后快速得到成功响应，随后自动进入对应岗位初筛池；正常简历无需 HR 逐份核对；失败任务保留投递事实、原简历和稳定错误并可人工处理。具体队列技术和重试策略在阶段开始前确认。

## 阶段 9：面试、Offer、录取和报告

### 当前方向

- 从阶段 7/8 已由 HR 通过初筛的 Application 开始后续招聘流程。
- 面试安排、反馈、复试和 AI 反馈总结。
- Offer、确认入职、拒绝、淘汰和主动退出。
- 初筛/候选人报告和完整阶段历史。

### 当前完成标准

一条真实投递可以从 HR 初筛推进到面试、Offer 和最终结果；高风险操作必须由 HR 确认；所有阶段变更可追溯；报告不得编造输入中不存在的信息。

## 阶段 10：首页综合 Agent

### 当前方向

- 在 Dashboard 建立自然语言 Agent 工作台。
- Agent 通过受控工具调用岗位、候选人、初筛、流程、报告和统计服务。
- 支持查询岗位 Top N 候选人和按需生成 JD 草稿。
- 区分查询、生成草稿、普通写入和高风险写入；写操作必须确认并审计。
- 使用 LangGraph 承载意图路由、工具选择、确认中断和恢复执行。
- 固定调用边界为 `Agent -> Tool -> Service -> PostgreSQL/Chroma`，LLM 只负责语言理解、工具选择和结果解释，确定性业务查询与计算由 Service 完成。
- Tools 使用强类型输入输出；阶段 10 不强制建设 MCP Server，只为未来外部调用预留适配层。
- 核心查询和分析支持模型不可用时的模板化降级。

### 当前完成标准

Agent 能基于真实业务数据完成核心查询和草稿生成；不能直接执行任意 SQL；未经确认不能产生正式写入或高风险流程变化；Tool 可独立测试并复用既有 Service；模型不可用时核心查询仍可返回可读结果。

## 阶段 11：知识库 RAG 和语义搜索

### 当前方向

- 上传和管理公司内部 PDF、DOCX、TXT 文件。
- 文本分段、Embedding、Chroma 索引和索引状态管理。
- 简历使用 `Resume.raw_text` 与 `Resume.parsed_snapshot` 生成带元数据的检索片段，不新增 PDF 转 Markdown 文件流程。
- 隔离 `resumes` 与 `company_knowledge` 集合。
- 支持带来源的公司知识问答和简历语义搜索。
- 支持查询分类、结构化过滤、Small-to-Big、合并去重和重排序；RAG 只负责召回，不替代正式初筛评分。
- 把知识检索作为受控工具接入首页 Agent。

### 当前完成标准

自然语言可以找到相关候选人或内部文件内容；回答包含来源文件和匹配片段；无法确认时明确说明不知道；公开投递用户不能访问内部知识；精确业务统计不错误启动 RAG，向量相似度不直接成为淘汰或录取依据。
