## 1. 文档定位与变更原则

本文定义阶段 5 之后的当前产品方向、业务主链路、核心对象、阶段顺序和总体完成标准。后续开发以本文作为路线基线，但允许在真实业务讨论、样本验证和实现反馈后修订。

每个阶段开始前必须执行“需求确认门禁”：

1. 先讨论该阶段的用户、业务场景、主流程和异常流程。
2. 明确本阶段包含什么、不包含什么，以及与前后阶段的依赖。
3. 固定数据字段、状态、权限、API 行为和失败语义。
4. 写出可操作、可观察的验收场景和自动化验证范围。
5. 将讨论结果写入独立阶段设计文档。
6. 获得用户明确确认后，才开始修改业务代码。

开发过程中发现新需求时，先判断它属于当前阶段、后续阶段还是总方案变更。任何会改变核心流程、数据模型、阶段边界或验收口径的内容，都必须先暂停扩展、重新讨论并更新文档，不能只在代码中悄悄改变设计。

2026-08-18 用户已确认旧 React + FastAPI + SQLite + Mock LLM 演示系统及演示数据全部退役。新版直接替代旧版，不再承担旧 Candidate、ScreeningResult、附件或旧状态的无损迁移义务；详见 `2026-08-18-legacy-system-retirement-decision.md`。

## 2. 最终产品定位

最终产品是一套覆盖“岗位创建 -> 候选人投递 -> 自动初筛 -> HR 决策 -> 面试 -> Offer -> 录取”的招聘管理系统，并在首页提供一个能够调用真实招聘业务能力、查询公司内部知识的综合 Agent。

最终产品由三条相互连接的主线组成：

1. 招聘业务全流程。
2. 首页综合 Agent。
3. 公司内部知识库 RAG 与简历语义搜索。

## 3. 招聘业务完整链路

```text
HR 创建并开放岗位
          ↓
候选人公开投递
          ↓
自动创建候选人和投递记录
          ↓
简历进入异步处理队列
          ↓
文件原文提取
          ↓
候选人信息结构化
          ↓
自动进入对应岗位的 AI 初筛池
          ↓
生成匹配分、推荐等级、优势、风险和证据
          ↓
HR 确认：通过 / 备选 / 淘汰
          ↓
安排面试 -> 记录反馈 -> 复试
          ↓
发放 Offer
          ↓
确认入职 / 淘汰 / 主动退出
```

公开投递不要求 HR 逐份核对 AI 结构化草稿。正常投递自动完成原文提取、结构化和岗位匹配；只有文件无法读取、结构化失败、岗位失效、信息严重不足或疑似重复等异常进入人工处理区。

阶段 5 已实现的“AI 草稿 -> HR 确认创建 Candidate”继续服务于 HR 内部手动新增场景。公开投递是另一条入口：先可靠保存投递事实，再异步完成 AI 处理，不能因模型失败丢失候选人或原简历。

## 4. 核心业务对象

### 4.1 Candidate 与 Application 分离

`Candidate` 表示候选人本人，负责姓名、标准化联系方式等稳定身份与去重信息。教育、工作、项目、技能和简历属于具体 Resume/Application 的岗位材料，不作为 Candidate 唯一全局真相。

新增 `Application` 表示候选人对某个岗位的一次具体投递，保存岗位、来源、投递时间、招聘阶段、AI 处理状态和 HR 决策。同一个 Candidate 可以拥有多个 Application，每次投递拥有独立的筛选、面试、Offer 和最终结果。

同一个 Candidate 投递不同岗位时使用不同 Resume 属于正常场景。系统不比较或合并不同简历的职业信息；每次评分只读取当前 Application 绑定的 Resume，不能被该 Candidate 的其他岗位简历污染。

候选人页面不是全部 Candidate 的原始名单，而是“HR 已明确通过初筛的 Application”业务视图：一行代表一个通过的岗位申请；同一个人申请不同岗位并分别通过时可以出现多行，人员详情再聚合展示其全部 Application。阶段 7 的每个新 Application 都必须绑定开放岗位、姓名、手机号、邮箱和当前 Resume；手机号与邮箱缺少任意一项都不能正式创建。

### 4.2 AI 处理状态与招聘阶段分离

阶段 7 的 AI 处理状态描述单次申请的评分状态：

- `not_started`
- `screening`
- `completed`
- `blocked`
- `failed`

阶段 8 接入公开投递和持久化队列后，再增加 `queued`、`extracting`、`structuring` 等异步处理状态。

HR 决策单独保存：

- `pending`
- `passed`
- `backup`
- `rejected`

阶段 7 的招聘业务阶段描述 HR 流程：

- `applied`
- `hr_review`
- `screening_passed`
- `backup`
- `rejected`

阶段 9 再启用后续阶段：

- `interview_scheduled`
- `interviewing`
- `second_interview`
- `offer`
- `hired`

AI 只给出评分、推荐等级和证据，不能自行改变 HR 决策或招聘阶段；硬性条件失败、信息未知和低分也不能自动淘汰。

### 4.3 最终核心对象集合

- `Job`：岗位及结构化要求。
- `Candidate`：候选人的稳定身份与去重信息，不承载跨岗位合并的职业画像。
- `Application`：一次岗位投递和招聘流程主记录。
- `Resume`：本次岗位使用的简历文件、原文、结构化草稿和 HR 确认资料。
- `ScreeningResult`：岗位匹配结果、证据和版本。
- `InterviewRecord`：面试安排与反馈。
- `OfferRecord`：Offer 信息与结果。
- `Report`：初筛或候选人报告。
- `StageHistory`：招聘阶段变更历史。
- `ActivityLog`：系统及 Agent 操作审计。
- `KnowledgeDocument`：内部知识文件及索引状态。
- `AgentSession` / `AgentAction`：Agent 会话与工具操作记录。

## 5. 岗位与 AI 初筛原则

阶段 6 由 HR 直接填写结构化岗位表单，不把“粘贴文本 -> AI 解析”作为必经步骤，也不在阶段 6 调用 DeepSeek。岗位至少包含基础信息、岗位职责、必备技能、加分技能、最低工作年限、学历要求、必备/加分经历、关键词、补充要求和 `draft/open/closed` 状态。

综合 Agent 后续可以按 HR 的明确要求生成 JD 草稿和结构化岗位要求，但只能生成草稿，必须经 HR 确认后保存，不能自动开放岗位。

AI 初筛采用 JD 驱动的固定 Service 工作流，不使用 LangGraph。岗位发布后，DeepSeek 先拆解完整 JD 的自由文本，程序再补齐结构化 JobRequirements 并合并去重，生成同一 JD 版本下稳定的基础评价事项。HR 可以只读查看，发现错误时修改原始 JD，不维护第二套 Rubric。

同一 Candidate 可以针对不同岗位使用不同简历。经历、学历、技能和项目不跨 Resume 比较或合并；确定性规则、模型输入、快照和输入指纹只使用当前 Application 绑定的 Resume，其他岗位简历和 Candidate 旧全局职业字段不得影响本次评分。

基础事项按 `required/preferred/general` 标记 JD 原始语气，统一逐项 `0—10` 分且不使用 `unknown`。1—10 分必须有可定位简历证据；0 分表示当前可用简历未体现，不代表候选人事实上不会。工作年限、相关年限和学历匹配由 DeepSeek 结合简历语义判断，后端不做确定性评分。

每份简历允许 0—5 个有证据、7—10 分、只产生正向影响的候选人额外亮点；AI 不得在 JD 之外创造新的扣分标准。DeepSeek 结合全部基础事项和额外亮点直接给出 `0—100` AI 岗位匹配建议分，Python 不按固定权重求和或限制上限。

AI 返回严格结构化 JSON，后端校验事项完整性、分数、证据定位、敏感信息和明显矛盾，React 渲染一份完整 AI 初筛报告。程序按 0—29、30—49、50—69、70—84、85—100 生成五档匹配标签；标签和分数都不改变 HR 决策。

初筛第一次满足岗位开放、评价事项就绪和 Resume 可用条件时在后台自动执行。JD 或 Resume 变化使当前报告过期，但不自动批量重评；HR 使用“重新评估”生成新报告。每个 Application 只保留最近一次成功报告和必要运行日志，新报告成功后替换，失败时旧成功报告保持不变。

Resume 不可可靠解析时不调用模型，不能把系统读取失败变成全部 0 分。姓名、联系方式、性别、出生日期、婚育、民族、籍贯和照片等信息在模型输入前移除；学校和公司名称可以作为相关语境，但不能脱离实际专业、职责、项目和成果，仅凭品牌直接判断能力或淘汰候选人。

## 6. 大批量投递与异步处理

公开投递接口只负责验证、可靠保存和快速返回，不同步等待 DeepSeek 完成全部处理。后台通过持久化任务队列顺序执行原文提取、结构化和岗位匹配。

```text
候选人提交申请
       ↓
FastAPI 保存 Candidate / Application / Resume 并返回成功
       ↓
任务写入 Redis 队列
       ↓
后台 Worker 提取、结构化和初筛
       ↓
保存结果并更新可观察状态
```

队列实现必须具备幂等、可重试、失败隔离和状态可观察性。单份失败不得影响其他投递，AI 失败不得删除候选人、Application、原文件或已经成功的历史结果。具体队列技术在阶段 8 需求确认时选择，不在本文提前锁定。

## 7. 招聘流程与人类决策边界

HR 初筛支持通过、备选、淘汰、重新筛选和查看证据。正式流程支持面试安排、面试反馈、复试、Offer、确认入职、候选人拒绝、HR 淘汰和主动退出，并保留完整阶段历史。

阶段 7 即完成 HR 的初筛通过、备选和淘汰决定，不再推迟到阶段 9。候选人页面“新增候选人”属于 HR 人工直通入口：HR 必须选择开放岗位并绑定简历，确认后立即形成 `passed/screening_passed` 的 Application，同时仍自动运行 AI 评分供参考；评分结果不能撤销 HR 的通过决定。AI 初筛中心“录入新申请”则先保持 `pending`，只有 HR 明确通过后才进入候选人页面。

录取、淘汰、发 Offer 和确认入职属于高风险操作，必须由 HR 明确确认。AI 和 Agent只能整理信息、生成草稿、提供建议或在确认后调用受控业务 API，不能独立做出最终招聘决策。

## 8. 首页综合 Agent

首页 Agent 是系统的自然语言操作入口，不是脱离业务数据的聊天机器人。它通过受控工具调用真实岗位、候选人、投递、筛选、报告、Dashboard 和知识库服务。

计划提供的工具类别：

- 岗位工具：查询岗位、生成 JD 草稿、创建/修改草稿、开放或关闭岗位。
- 候选人工具：查询候选人、查看详情、条件筛选和语义搜索。
- 初筛工具：查询岗位 Top N、启动初筛、查看或解释结果。
- 流程工具：查询待办、安排面试、推进阶段和查看 Offer/入职状态。
- 报告工具：生成候选人报告、排名和招聘进展摘要。
- Dashboard 工具：查询投递、初筛、面试、Offer 和异常任务统计。
- 知识库工具：查询公司制度、招聘规范、岗位模板和内部业务文件。

Agent 操作分级：

| 类型 | 示例 | 规则 |
| --- | --- | --- |
| 查询 | 查询候选人、岗位、统计 | 可直接执行 |
| 生成草稿 | 生成 JD、报告、面试问题 | 可生成，但不直接产生正式业务结果 |
| 普通写入 | 创建岗位草稿、启动初筛 | 展示预览并确认 |
| 高风险操作 | 淘汰、发 Offer、确认入职 | 必须明确确认并记录审计 |

Agent 不能直接执行任意 SQL 或文件系统操作。统一调用链为 `Agent -> Tool -> Service -> PostgreSQL/Chroma`：LLM 负责理解自然语言、选择工具和解释结果，查询、统计、评分规则和状态变更由确定性、可测试的 Service 完成。写操作必须写入日志；LLM 不可用时，核心查询和分析应保留模板化降级能力。综合 Agent 确有意图路由、工具选择、确认中断、恢复执行和多步骤编排需求，因此是适合使用 LangGraph 的模块。

Tools 是阶段 10 的必选能力，但 MCP 不是当前 MVP 的必选项。内部 Tool 使用强类型输入输出并复用现有 Service；只有未来出现外部 Agent、IDE 或第三方系统调用需求时，才在同一套 Tool/Service 之上增加薄的 MCP Adapter，不把 MCP Server 建成核心业务层。

## 9. RAG 与知识库

内部知识库支持 PDF、DOCX、TXT 等公司文件，执行安全上传、原文提取、分段、Embedding、Chroma 索引和带来源检索。

简历 RAG 不增加 PDF 转 Markdown 文件流程，也不替换阶段 4、5 已稳定的 `Resume.raw_text` 和 `Resume.parsed_snapshot`。索引时根据原文与结构化字段按工作、项目、教育、技能等章节生成检索片段，并保存 `candidate_id`、`resume_id`、章节和时间等元数据；允许在内存中使用 Markdown 风格组织片段，但不产生 `.md` 文件。

至少隔离两个集合：

- `resumes`：候选人简历语义搜索。
- `company_knowledge`：公司制度、招聘规范、员工手册、岗位模板和业务资料。

知识回答必须返回来源文件和匹配片段；无法可靠确认时明确说明不知道。公司内部知识与简历数据不得向公开投递页面暴露，具体权限模型在阶段 11、12 开始前讨论确认。

RAG 负责候选人召回和知识检索，不代替正式初筛评分。候选人搜索采用“结构化过滤 -> 语义召回 -> 去重重排 -> 取回完整上下文”的链路；岗位 Top N 优先读取有效的正式 ScreeningResult，复杂模糊条件才启动简历语义检索。

## 10. 阶段 6—12 路线

### 阶段 6：结构化岗位管理

- 严格、版本化的岗位要求 Schema。
- HR 直接填写岗位，不使用 AI 解析。
- 草稿、开放、关闭状态及业务校验。
- 前端真实创建、编辑、开放和关闭。
- AI 初筛中心只读取开放岗位。

预计 7—10 个工作日。

### 阶段 7：Application 与 AI 初筛底座

- 保留 Application、Resume 隔离和阶段历史，分离人员、申请、AI 状态、HR 决策与招聘阶段。
- 候选人页面直通录入与 AI 初筛中心待审核录入都必须选择开放岗位，并要求姓名、手机号、邮箱和当前 Resume。
- 候选人页面只展示 HR 已通过的 Application；同一 Candidate 的不同岗位申请独立评分、独立决策。
- 使用 AI 拆解自由文本、程序补齐结构化要求的混合方案，生成稳定、只读的 JD 基础评价事项；不在本阶段引入 LangGraph。
- 基础事项逐项 `0—10` 且不使用 `unknown`；候选人额外亮点只输出有证据的 7—10 分正向事项。
- DeepSeek 直接给出 `0—100` 综合匹配分，后端不加权重算；严格校验 JSON、事项完整性、证据、公平性和明显矛盾。
- React 渲染完整 AI 初筛报告；每个 Application 只保留最近一次成功报告和必要运行日志。
- 实现 HR 通过、备选、淘汰、反转、作废及本地未认证审计边界。
- 首次满足条件时后台自动初筛；提供单个与最多 20 份小批量重新评估，批内单份失败互不影响。
- 所有 Application 使用同一新版合同并绑定当前 Resume，不保留 `legacy_migration`、`legacy_stage`、无 Resume 例外或旧评分兼容响应。
- 先删除旧 Rubric 代码和业务数据，再开发新评价计划与报告链路。
- 使用 20 份不同 JD 和至少 20 组脱敏 JD/Resume 样本完成拆解、人工方向、重复稳定性、安全、真实 PostgreSQL、真实 DeepSeek 与浏览器验收。

专项设计与执行顺序见 `2026-08-20-stage7-jd-driven-ai-screening-redesign.md`；旧方案已归档到 `../archive/specs/2026-08-17-stage7-application-ai-screening-design.md`，只保留历史实现记录。

预计 10—15 个工作日。

### 阶段 8：公开投递和自动初筛

- 开放岗位投递。
- 投递者必须填写姓名、手机号和邮箱并上传简历，自动创建或安全复用 Candidate，再创建 Application、Resume。
- Redis 异步队列和 Worker。
- 复用阶段 7 的 JD 评价计划和 AI 报告引擎，自动完成原文提取、结构化和岗位匹配。
- HR 初筛处理池和异常任务处理区。

预计 10—15 个工作日。

### 阶段 9：面试、Offer、录取和报告

- 从阶段 7/8 已由 HR 通过初筛的 Application 开始后续流程。
- 面试安排、反馈、复试和 AI 反馈总结。
- Offer、入职、拒绝、淘汰和退出。
- 初筛/候选人报告及完整阶段历史。

完成后招聘业务主链路闭环。预计 10 个工作日。

### 阶段 10：首页综合 Agent

- Agent 会话、意图识别和业务工具注册。
- 候选人、岗位、筛选、报告、流程和统计工具。
- JD 草稿生成。
- 写操作确认、安全中断恢复和审计。
- 内部 Tool 采用强类型输入输出并调用业务 Service；LLM 不直接计算业务数据。
- 核心查询与分析具备模型不可用时的模板化降级能力。
- 首页 Agent 工作台。

预计 10—15 个工作日。

### 阶段 11：知识库 RAG 和语义搜索

- 内部文件上传、分段、向量化和索引状态。
- 公司知识库问答与来源引用。
- 简历语义搜索。
- 使用 `raw_text/parsed_snapshot` 生成带元数据的简历检索片段，不建设 PDF 转 Markdown 文件流程。
- 查询分类、结构化过滤、Small-to-Big、去重重排和命中片段引用。
- 知识集合与权限隔离。
- Agent 接入知识库工具。

预计 7—10 个工作日。

### 阶段 12：质量、权限、部署和交付

- HR 登录、基础角色和 Agent 工具权限。
- 统一错误处理、审计、隐私和数据保留策略。
- Docker Compose 与端到端测试。
- 新版受控 seed、README、使用说明和唯一运行入口收口。

预计 10 个工作日。

## 12. 最终验收场景

1. HR 创建并开放岗位 A。
2. 候选人公开投递岗位 A，接口快速返回成功。
3. 后台自动读取、结构化简历并进入岗位 A 初筛池。
4. 系统生成分数、等级、优势、风险、理由和证据。
5. HR 通过初筛、安排面试、记录反馈、发放 Offer 并确认入职。
6. 全部阶段变化和高风险操作可追溯。
7. HR 在首页询问“岗位 A 最匹配的 5 个人”，Agent 返回真实排序和依据。
8. HR 要求 Agent 生成 JD，Agent 返回草稿并等待确认。
9. HR 查询内部制度，Agent 通过 RAG 返回带来源答案。
10. AI 或队列失败不丢失候选人、投递、原简历或历史成功结果。
11. 未授权用户无法访问后台数据或执行高风险操作。

## 13. 当前明确不承诺的内容

- AI 自动录取或自动淘汰。
- 不会把 AI 解析 JD 设为阶段 6 的强制步骤。
- 未经确认由 Agent 开放岗位、推进高风险阶段或发 Offer。
- 在阶段需求讨论前提前锁定队列框架、评分权重或完整权限矩阵。
- 早期 MVP 直接建设复杂多租户、外部邮件/日历或商业 ATS 集成。
- 为简历解析新增 PDF 转 Markdown 文件流程。
- 把向量相似度直接作为正式初筛、淘汰或录取依据。
- 在没有外部调用需求时提前把内部 Tools 全部包装成 MCP Server。

## 14. 外部参考项目的使用原则

阶段 6—12 的外部参考对比、项目差距、借鉴原因和不借鉴项统一记录在 `../research/2026-08-15-github-recruiting-project-comparison.md`。当前总体取舍为：
