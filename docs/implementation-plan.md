# HR Agent 招聘提效平台实施计划

> 日期：2026-07-15  
> 最近修订：2026-08-13（阶段 5 三类经历人工确认导入已完成）
> 状态：阶段 4 已完成；阶段 5 前五小步及前端接入前四小步已完成，下一步为技能候选和未建模内容安全展示
> 权威设计文档：`docs/specs/2026-07-15-hr-agent-platform-design.md`  
> 目的：把最终成品拆成可执行阶段，后续开发按阶段推进、验收和记录。

## 总体目标

把现有旧版招聘助手重构为面向公司内部 HR 团队的 AI 招聘工作台。最终产品要支持简历上传、简历结构化解析、岗位 JD 管理、AI 匹配打分、初筛报告生成、自然语言智能助手、候选人公开投递和基础数据看板。

技术目标是从旧版 `React + FastAPI + SQLite + Mock LLM` 升级为：

- 前端：React 18 + TypeScript + Ant Design 5 + Vite + zustand
- 后端：FastAPI + SQLAlchemy 2.0 + Pydantic v2 + Alembic
- 数据：PostgreSQL 16 + Redis + Chroma
- AI：DeepSeek API；LangGraph 按真实工作流复杂度使用，不强制包装普通单次模型调用
- 部署：Docker Compose

核心原则：先做可靠的招聘业务闭环，再把 AI 放进关键节点。不要先追求“会聊天”，而是先保证 HR 可以真实完成“上传简历 -> 解析 -> 匹配 -> 报告”的主流程。

## 里程碑

| 里程碑 | 目标 | 完成标志 |
| --- | --- | --- |
| M1 基础骨架 | 前后端、数据库和基础服务跑起来 | 前端能打开，后端 `/docs` 可访问，PostgreSQL/Redis/Chroma 可连接 |

## 阶段 0：项目对齐与基线整理

### 要做什么

1. 确认权威设计文档路径。
2. 检查旧版项目结构和关键文件。
3. 梳理可迁移资产、需重写模块、保留历史模块。
4. 建立或更新项目状态文档。
5. 明确后续阶段的执行顺序和验收口径。

### 为什么这样做

当前项目不是空项目，而是已有一版演示系统。旧系统里有很多可复用资产，比如 Prompt、文件解析、候选人投递页和规则评分逻辑。但旧系统的架构和最终目标不一致，如果直接在旧代码上堆功能，很容易变成“能跑但不好维护”的系统。

阶段 0 的价值是先划清边界：哪些东西要搬家，哪些东西要重写，哪些东西只作为参考。这样后面每一步都有依据。

### 可能遇到的问题

- 旧版 `PROJECT_STATE.md` 显示“已完成”，但这是旧演示版本，不代表新架构完成。
- 旧版后端目录是 `routers/`、`services/` 结构，新设计要求 `api/`、`core/`、`agents/`、`rag/` 等分层。
- 旧版数据库默认偏 SQLite，本次目标是 PostgreSQL + Alembic。
- 旧版 AI 服务职责混杂，需要按业务边界重写；普通单次模型能力放在 Service，确有条件路由、循环或多工具协作的复杂流程才使用 LangGraph。

### 验收标准

- `CLAUDE.md` 指向的设计文档存在。
- 项目状态文档明确标记“架构重建阶段”。
- 迁移清单清楚列出复用、重写和参考文件。
- 后续阶段能按计划继续，不需要重新判断方向。

## 阶段 1：项目骨架与基础设施

### 要做什么

后端：

- 建立新后端分层：`api/`、`core/`、`models/`、`schemas/`、`services/`、`agents/`、`rag/`。
- 创建 FastAPI 入口和路由挂载。
- 建立配置管理：`.env`、`.env.example`、`core/config.py`。
- 建立 PostgreSQL 异步连接：`core/database.py`。
- 建立 Redis 连接：`core/redis.py`。
- 建立 DeepSeek/OpenAI 兼容客户端：`core/llm.py`。
- 初始化 Alembic。

前端：

- 整理 Vite + React + TypeScript 项目结构。
- 接入 Ant Design 5 和主题 token。
- 建立主 Layout：侧边栏、顶部栏、内容区。
- 建立路由和 API client。
- 预留页面目录：Dashboard、Resume、Screening、Jobs、Apply。

基础设施：

- 更新 Docker Compose：PostgreSQL、Redis、Chroma。
- 更新 README 启动方式。

### 为什么这样做

先搭骨架，是为了让后续所有功能都有地方放。AI 工作流、数据库模型、前端页面都不能散落在旧结构里，否则后期维护成本会很高。

### 可能遇到的问题

- 旧文件和新目录并存时容易导入冲突。
- Windows 本地路径和 Docker 路径可能不一致。
- PostgreSQL 迁移时要避免旧 SQLite 逻辑继续被引用。

### 验收标准

- 后端能启动，`/docs` 可访问。
- 前端能启动并看到基础布局。
- Docker 基础服务能启动。
- 不要求业务功能完整，但新结构要稳定。

## 阶段 2：数据库模型和核心业务对象

### 要做什么

建立核心表和对应模型：

- `candidates`
- `jobs`
- `resumes`
- `education`
- `work_experience`
- `project_experience`
- `screening_results`
- `reports`
- `activity_logs`

同时完成：

- SQLAlchemy models
- Pydantic schemas
- Alembic migration
- 基础 CRUD services
- 基础 API

### 为什么这样做

AI 结果最终必须落到业务数据里。候选人、岗位、筛选结果和报告是系统的主干，先把数据结构定清楚，后面的 AI 和前端才有稳定接口。

### 可能遇到的问题

- 简历解析结果既需要结构化字段，也需要保留原始 JSON。
- 工作经历、项目经历、教育经历是多条记录，不适合全部塞进候选人主表。
- JSONB 字段灵活，但不能滥用，否则查询和统计会变困难。

### 验收标准

- 可以创建、查询、更新岗位和候选人。
- 数据真实写入 PostgreSQL。
- Alembic 可以正常建表和回滚。

### 要做什么

建立以下页面的可点击骨架：

- Dashboard 工作台
- 简历管理页

### 为什么这样做

- B 端页面容易信息过载，要控制信息层级。
- 不要把工作台做成营销首页，第一屏应该是实际工作入口。

### 验收标准

- 用户可以从菜单进入所有核心页面。
- 页面结构和最终业务流一致。
- 页面可以使用 mock 或空数据，但不能是零散 demo。

## 阶段 4：简历上传与文件解析

### 要做什么

- 通过 `POST /api/v2/resumes/upload` 安全接收 PDF、DOCX、TXT，校验真实文件类型、大小和私有存储路径。
- 通过 `POST /api/v2/resumes/{resume_id}/extract-text` 把文件转换为 `Resume.raw_text`，记录 `uploaded/parsing/parsed/failed` 文件解析状态和稳定错误。
- 支持 `candidate_id = NULL` 的待绑定 Resume，使 HR 可以先上传和提取原文，再确认候选人。
- 通过 `POST /api/v2/candidates/from-resume` 在一个数据库事务中创建 Candidate、三类经历并绑定 Resume；阶段 4 不识别结构化字段。
- 提供原始简历的安全查看/下载、主动放弃未绑定 Resume 和 24 小时过期自动清理。
- 旧 `/api/resume/*` 与新版 `/api/v2/resumes/*` 隔离并存，避免破坏旧演示系统。

### 为什么这样做

简历上传是整条链路的入口。阶段 4 只负责“文件 → 可信原文”，并保证文件、数据库记录和候选人确认绑定之间的安全边界；阶段 5 才负责“原文 → 结构化草稿”。

### 可能遇到的问题

- PDF 有扫描件、表格、乱码等情况。
- DOCX 可能有表格、合并单元格或复杂压缩包结构。
- 上传失败、解析失败需要明确状态，不应该悄悄吞掉错误。
- 文件系统与 PostgreSQL 无法组成真正的跨系统原子事务，需要补偿清理和孤立文件边界。
- 未绑定 Resume 需要主动放弃和过期清理，同时不能误删已绑定或正在使用的文件。

### 验收标准

- PDF、DOCX、TXT 至少各有一个样例能成功解析。
- 原始文件、元数据、`raw_text` 和文件解析状态真实保存，读取和下载不暴露私有路径。
- 待绑定 Resume 能在 HR 确认后与 Candidate 及经历记录单事务保存，失败不会留下半绑定数据。
- 主动放弃和 24 小时清理不会删除已绑定 Resume，数据库失败时能够补偿恢复文件。
- 前端能展示上传、提取、失败、查看、下载、放弃和确认创建的真实状态。

## 阶段 5：大模型简历结构化提取与表单辅助填写

### 要做什么

阶段 5 复用阶段 4 已保存的 `Resume.raw_text`，不重复处理文件。第一版不使用 Agent 或 LangGraph，建立普通 `ResumeStructureService`：

1. 定义版本化、严格的 `ResumeParseDraft`，包含基本资料、教育、工作、项目、技能、证书、自我评价、警告和缺失字段。
2. 通过模型 Adapter 正常只调用一次 DeepSeek，使用 JSON Output，把完整原文转换成统一草稿。
3. 依次执行 JSON 解析、Pydantic 严格 Schema 校验和日期、重复项、长度、空记录等业务校验；未知字段禁止静默进入系统。
4. 成功草稿保存到 `Resume.parsed_snapshot`；新增独立的结构化识别状态、错误和版本字段，不复用阶段 4 的文件 `parse_status`。
5. 新增 `POST /api/v2/resumes/{resume_id}/structure`。已有成功草稿时默认直接返回，只有 HR 明确点击“重新识别”才再次调用模型；同一 Resume 并发识别返回 `409`。
6. 前端在阶段 4 原文提取成功后触发识别，将 AI 结果只补充到空字段。HR 已填写的普通字段不得覆盖；已有经历列表时不得静默拼接，由 HR 选择是否导入。
7. AI 只生成草稿，不直接创建或改写 Candidate 及三类经历；HR 检查、修改并确认后，才复用现有单事务接口创建 Candidate 并绑定 Resume。

完整设计与字段、状态、API、异常和验收规则见 `docs/specs/2026-08-12-stage5-resume-structure-design.md`。

### 为什么这样做

当前输入和输出都是固定的：`Resume.raw_text -> ResumeParseDraft`。第一版用一次模型调用即可验证真实简历上的完整性、延迟和费用；此时引入 Agent 或多节点 LangGraph 会增加调用次数和调试成本，但没有相应的自主决策价值。通过稳定的 Service/API 抽象保留演进空间，只有真实样本证明存在稳定的局部遗漏或局部重试需求后，才评估内部升级为多节点工作流。

### 可能遇到的问题

- LLM 输出不是合法 JSON。
- JSON 合法但字段类型、日期关系或业务内容不合法。
- 模型可能返回空内容、输出被截断、超时、限流或服务错误。
- 同一信息在简历里重复出现。
- 某些字段无法确定，要填 `null`，不能编造。
- AI 结果可能与 HR 已填写字段或经历列表冲突。
- 大模型服务失败不能破坏阶段 4 已保存的原文件和原文。

### 验收标准

- 每次正常识别只调用一次 DeepSeek，不使用 Agent 或 LangGraph。
- 模型错误、空响应和非法输出无法写入草稿或自动填表；失败后原文件、原文和人工输入保持不变。
- 合法草稿写入 `Resume.parsed_snapshot`，页面刷新后可以重新取得；结构化状态与阶段 4 文件解析状态语义分离。
- 前端能辅助填写基本资料、教育、工作、项目和技能，但不覆盖 HR 已填写字段，也不静默合并已有经历列表。
- 应聘岗位、来源和招聘状态不由模型猜测；性别和年龄不得用于后续评分。
- 学校名称在本阶段只按原文提取，不推断 985/211；后续如用于初筛，必须通过可追溯的标准院校数据判断。
- AI 不直接创建 Candidate；只有 HR 最终确认才写入正式候选人和经历表。
- Fake Adapter 的自动化测试、真实 DeepSeek + FastAPI + PostgreSQL 验证、前端生产构建和人工操作验收均通过。

## 阶段 6：岗位 JD 管理

### 要做什么

- 创建、编辑、关闭岗位。
- 保存原始 JD。
- 保存结构化岗位要求。
- 支持硬性要求和加分项。

### 为什么这样做

AI 匹配必须有明确目标。岗位 JD 既要保存原文，也要有结构化要求，方便后续做硬性条件判断和多维评分。

### 可能遇到的问题

- JD 文本可能很自由，结构化要求不一定完整。
- HR 需要能人工修正 AI 解析出的岗位要求。

### 验收标准

- HR 可以创建一个完整岗位。
- AI 筛选中心可以选择该岗位。

## 阶段 7：JD 匹配打分工作流

### 要做什么

建立 `jd_match` 工作流：

- `parse_jd_requirements`
- `hard_require_check`
- `skill_match`
- `experience_match`
- `project_match`
- `risk_analysis`
- `overall_score`
- `save_screening_result`

院校条件如确有岗位业务需求，应使用“学校名称标准化 + 可追溯院校目录”取得 985/211/双一流等标签，再结合岗位配置判断。不得依赖大模型记忆自由推断；院校标签更适合作为可解释的匹配维度或加分项，不应由系统据此自动淘汰候选人。

### 为什么这样做

招聘筛选不能只给一个总分。HR 需要知道为什么推荐、为什么有风险、哪些条件不满足。多维评分比一次性打分更可解释。

### 可能遇到的问题

- AI 可能对硬性条件判断过严或过松。
- 分数看起来精确，但实际依据不足。
- 不能用性别、年龄、民族、婚育等敏感信息做评估。

### 验收标准

- 可对多个候选人批量筛选。
- 每个结果有总分、推荐等级、优势、风险和理由。
- 结果写入 `screening_results`。

## 阶段 8：初筛报告生成

### 要做什么

- 建立 `report_gen` 工作流。
- 生成 Markdown 报告。
- 支持报告保存和查看。
- 后续支持 Word/PDF 导出。

### 为什么这样做

HR 最终需要把筛选结果交给用人部门。报告是 AI 能力转化成业务协作材料的关键出口。

### 可能遇到的问题

- 报告不能编造简历里没有的信息。
- 结论要专业，但不能替 HR 做最终录用决定。
- 导出 PDF/Word 时版式需要单独验证。

### 验收标准

- 从筛选结果一键生成报告。
- 报告结构完整、语言专业、可读。
- 报告可以再次打开查看。

## 阶段 9：智能助手

### 要做什么

建立 `smart_assistant` 工作流，支持：

- 查询候选人
- 触发筛选
- 生成报告
- 查询统计
- 通用问答

### 为什么这样做

智能助手不是单纯聊天窗口，而是系统能力的自然语言入口。它要能理解 HR 的意图，并路由到真实业务服务。

### 可能遇到的问题

- 意图识别错误会触发错误操作。
- 需要区分“查询类”和“写入类”操作。
- 流式输出需要和前端状态配合。

### 验收标准

- 至少 4 类核心意图能正确执行。
- 能返回候选人、筛选结果或报告动作。

## 阶段 10：RAG 和语义搜索

### 要做什么

- 简历文本分段。
- 生成 embedding。
- 写入 Chroma。
- 支持自然语言搜索候选人。
- 返回匹配片段和候选人列表。

### 为什么这样做

HR 经常不是按精确字段查人，而是用模糊描述找人，例如“做过高并发微服务的 Java 候选人”。向量检索能解决这类语义查询。

### 可能遇到的问题

- 语义匹配可能召回不准，需要结合结构化过滤。
- embedding 更新要和简历更新保持一致。

### 验收标准

- 自然语言能搜出相关候选人。
- 返回结果能解释匹配依据。

## 阶段 11：候选人投递页

### 要做什么

- 迁移并升级 `ApplyForm.tsx`。
- 展示开放岗位。
- 候选人填写信息并上传简历。
- 提交后进入候选人库和解析流程。

### 为什么这样做

这让候选人入口和 HR 后台打通。外部投递的数据可以直接进入同一套解析、筛选和报告流程。

### 可能遇到的问题

- 公开页面要控制接口滥用和文件大小。
- 表单字段要尽量简洁，减少候选人填写负担。

### 验收标准

- 候选人可以完成一次真实投递。
- HR 后台能看到新候选人。

## 阶段 12：质量、权限、部署和验收

### 要做什么

- 登录和基础权限。
- 错误处理和日志。
- 操作日志。
- API 测试和前端构建测试。
- Docker Compose 一键启动。
- 演示数据准备。
- README 和使用说明。

### 为什么这样做

产品要交付，不能只在开发机上能跑。部署、错误处理、权限和文档决定了它能不能被别人稳定使用。

### 可能遇到的问题

- 本地和 Docker 环境配置不同。
- AI API 不可用时需要有明确降级策略。
